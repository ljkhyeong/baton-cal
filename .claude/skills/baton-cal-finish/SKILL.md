# BATON CAL 작업 마무리

## 1. 종료 검사와 검토

```bash
python3 -B scripts/agent_feedback.py final --session <작업명>
```

출력된 `review.diff` 전체를 baton-cal-review 기준으로 읽는다. 결함을 고쳤다면 `files`와 `final`을 다시 실행한다.
검사가 실패하면 같은 편집을 다시 적용하지 말고 현재 파일과 로그를 확인한다. 권한·Java·의존성 문제는 환경을
먼저 고친 뒤 실패한 범위만 재실행한다.

## 2. 문서 갱신

- 제품 동작은 `docs/PRD/`, 구조 결정은 `docs/ADR/`, 실행·운영 절차는 `README.md`·`docs/operations.md`에 반영한다.
- `HANDOFF.md`는 baton-cal-docs의 인수인계 기준을 따른다. 바뀐 현재 상태, 최신 관련 검증, 남은 작업, 현재 제한만
  남기고 대체된 기록은 지운다. 구현·검증·배포하지 않은 내용을 완료로 쓰지 않는다.

## 3. 커밋

- 본인 변경만 커밋한다. `git status --short`로 다른 변경을 확인하고 경로를 지정해 스테이징한다. `git add -A`는 쓰지 않는다.
- 목적별로 나눠 `종류: 한글 요약` 형식으로 쓴다. 종류는 `기능`, `수정`, `문서`, `테스트`, `설정`, `빌드`, `배포`,
  `운영`, `리팩터`다.
- 기능·수정 커밋에는 그 동작의 테스트와 PRD·계약 갱신을 함께 넣는다. 기존 동작의 테스트 보강만이면 `테스트`,
  인수인계·안내 문서만이면 `문서`로 분리한다.
- 요약은 결과 중심으로 짧게 쓴다. 예: `기능: 일정 묶음 수신과 시즌별 일괄 투영`, `테스트: 알림 수신기 준비 후 스모크 실행`.
- 커밋 전에 스테이징한 diff를 다시 확인한다. 비밀값·로컬 임시 파일(`.env.integration.local`, `build/`)이 없어야 한다.

## 4. 푸시와 PR

사용자가 푸시나 PR을 요청한 경우에만 진행한다. 병합·공식 릴리스·운영 배포는 별도 요청이 있어야 한다.

- 작업 브랜치는 `codex/<주제>` 형식이다. main에서 작업했다면 새 브랜치를 만든 뒤 푸시한다.
- `git push -u origin <브랜치>`로 올린다. 강제 푸시는 사용자가 명시한 경우에만 한다.
- PR 제목은 커밋과 같은 `종류: 한글 요약` 형식이다. 본문은 파일로 작성해 `gh pr create --body-file <파일>`로 넘긴다.
- 본문에는 변경 목적을 한 문단으로 쓰고, 아래에 변경 사항·검증 명령과 결과·재사용한 결과·남은 작업을 목록으로 적는다.
- PR을 만든 뒤 필수 CI 완료를 확인한다. 실패하면 baton-cal-ci-fix를 사용한다.

## 5. 보고
