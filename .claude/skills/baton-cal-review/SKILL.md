# BATON CAL 변경 검토

읽기 전용으로 검토한다. 파일 수정·커밋·푸시·리뷰 댓글 게시는 사용자가 따로 요청할 때만 한다.
`AGENTS.md`의 서비스 계약과 구현 규칙을 기준으로 삼는다.

## 대상 확정

| 대상 | 방법 |
| --- | --- |
| 진행 중인 작업 | `python3 -B scripts/agent_feedback.py final --session <작업명>`이 출력한 `review.diff` |
| 브랜치 | upstream이 앞서 있으면 upstream, 아니면 로컬 기준 브랜치로 `git merge-base HEAD <기준>`을 구해 `git diff <merge-base>` |
| 커밋 | `git show <커밋>` |
| PR | `gh pr diff <번호>`. 주변 코드는 `git fetch origin pull/<번호>/head` 뒤 `git show FETCH_HEAD:<경로>`로 읽는다 |

diff는 끝까지 읽는다. 길면 파일별로 나눠 모두 확인하고, 각 변경 경로의 호출 위치와 관련 테스트를 함께 본다.
ArchUnit 통과를 전체 리뷰로 대신하지 않는다.

## 확인 항목

- 이벤트 순서: 같은 재전달은 상태를 바꾸지 않고 낮은 개정 번호는 무시한다. `UID`를 유지하고 원본 개정 번호가
  증가할 때만 `SEQUENCE`를 높인다. 삭제는 취소 표식으로 남긴다.
- 투영 안정성: 같은 투영은 같은 바이트·`ETag`·`Last-Modified`를 유지한다. 골든 변경에는 의도와 `ETag` 영향 근거가 있다.
- 시간: IANA 시간대, UTC·현지 시각·종일 날짜의 의미, 배타적 종일 종료일, `Clock` 주입을 지킨다.
- 비밀값: 토큰 원문·내부 Bearer·작업공간 키가 로그·예외 메시지·메트릭 라벨·추적·DB·캘린더 본문에 들어가지 않는다.
  토큰은 발급 응답에서만 노출하고 해시만 저장하며 회전·폐기 즉시 이전 토큰이 무효가 된다.
- 공개 피드: `ACTIVE`·토큰 해시·구독 세대가 일치할 때만 응답하고 오류 응답은 `Cache-Control: no-store`다.
- 계층·DB: ADR-0003 규칙 외에도 트랜잭션 경계, 잠금 순서, CAS, DB 키로 판정하는 동시 생성을 확인한다.
  적용된 마이그레이션을 수정하지 않았고 새 마이그레이션은 기존 데이터를 보존한다.
- 검증 위치: 같은 책임의 검증은 한 곳에 둔다. HTTP 입력·도메인 규칙·DB 무결성처럼 책임이 다른 검증은 유지한다.
- 코드량: 표준 라이브러리·JDK·Spring·고정 라이브러리 API로 대체할 수 있는 자체 구현, 불필요한 추상화·DTO·변환이 없다.
  계약을 보완한 코드에는 그 차이를 고정하는 회귀 테스트가 있다.
- 계약·문서: 계약 변경 시 PRD-0002·스키마·예시·골든·`contracts/VERSION`이 맞다. 제품 동작은 PRD, 구조 결정은
  ADR에 반영했고 `HANDOFF.md`가 구현·검증하지 않은 내용을 완료로 쓰지 않는다.

## 보고 기준

다음을 모두 만족할 때만 결함으로 보고한다.

- 정확성·보안·성능·유지보수에 실제 영향이 있다.
- 이번 변경이 원인이며 영향받는 시나리오나 호출 경로를 코드로 보일 수 있다.
- 작성자가 알면 고칠 만한 구체적인 문제다.

추측, 기존 문제, 의도된 동작 변경, 이해를 방해하지 않는 문체 취향은 보고하지 않는다.

## 출력

심각도 순으로 한 건씩 쓴다.

`[P1] 명령형 제목 — path/to/file.kt:줄`

제목 뒤에 영향받는 시나리오와 잘못된 이유를 한 문단으로 쓴다. 인용 범위는 diff와 겹치게 최소로 잡는다.

- `P0`: 출시를 막는 치명적 결함
- `P1`: 바로 고쳐야 하는 결함
- `P2`: 고쳐야 하는 일반 결함
- `P3`: 영향은 작지만 고칠 가치가 있는 결함

결함이 없으면 `결함 없음.`이라고 쓴다. 채우기 위한 지적은 만들지 않는다. 마지막에 짧은 총평과
테스트 공백·남은 위험을 적는다.
