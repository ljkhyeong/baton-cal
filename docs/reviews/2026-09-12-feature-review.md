HEAD 개선은 기존 구독 URL과 GET·304·404 동작을 유지한다. DB 스키마나 외부 서비스를 추가하지 않는다.
HEAD 회귀 테스트는 GET과의 헤더 일치, UTF-8 바이트 길이, 조건부 조회 우선순위, 빈 피드,
잘못된 주소·재발급·해제·이전 세대 토큰 차단을 확인한다. 조회 비용은 본문 조회가 호출되지 않는지 검증하며,
응답 속도 개선율은 별도로 측정하지 않는다.

DB 연결 실패 개선은 기존 Spring 예외 분류와 `api-error.v1` 응답을 사용한다. 서버 내부에서 재시도하지 않는다.
실제 연결을 모두 점유해 발급·피드 조회의 `503`을 확인하고, 연결 반환 후 정상 조회·구독 생성과 중복 저장 방지를 검증한다.

구독 생성 개선은 기존 DB 기본키와 트랜잭션을 사용하며 API와 스키마는 유지한다. 신규 요청에는 ID 조회가
한 번 추가된다. 동시 생성, 다른 시즌에 같은 ID를 사용한 요청의 충돌, 캘린더 생성 실패 후 같은 ID의 재시도를 검증한다.

HTTP 캐시는 `404` 같은 실패 결과도 저장할 수 있다. 상태 조회의 오류가 저장되면 자원이 생성된 뒤에도
이전 결과를 재사용할 수 있으므로 공통 상태 오류 처리에서 저장을 금지한다.
[RFC 9111 §2](https://www.rfc-editor.org/rfc/rfc9111.html#section-2),
[§5.2.2.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5).
실제 캐시 장애를 관측한 것은 아니며, 기존 HTTP 테스트에서 헤더와 `404 → 생성 → 200` 흐름을 검증한다.

같은 초의 일정 변경은 기존 계약대로 강한 ETag로 구분한다. 복구 상태 조회는 저장된 완료 기록과 현재
상태 진단을 구분하며 자동으로 복구 모드를 해제하지 않는다. 이 범위에는 새 API나 추가 검증 로직을 넣지 않는다.
최종 검증 결과는 [인수인계](../../HANDOFF.md)에 기록한다.
