# BATON CAL 기능 추가·개선 검토

- 검토일: 2026-09-05
- 기준 커밋: `978f0d4`
- 상태: 구현 우선순위 제안. 채택된 제품 계약이나 완료된 구현을 뜻하지 않는다.
- 범위: CAL 코드·테스트·PRD·ADR·운영 스크립트. BATON 저장소와 운영 환경은 직접 검토하지 않았다.

## 판단

시즌 피드, 다섯 시간 형태, 변경·취소·재활성화, 중복·역순 전달, 조건부 GET, 구독 회전·폐기,
시즌 이름, 상태 조회와 복구 매니페스트는 구현되어 있다. 다음 작업은 구독 실패 복구, 실제 캘린더
앱 사용성, 복원 절차 검증을 우선하는 것이 좋다.

아래 P1은 사용자에게 구독 기능을 제공하거나 공개 배포하기 전에 우선 처리할 항목이고, P2는
운영 진단과 예상 데이터 규모에 맞춰 진행할 항목이다. 버그 심각도 판정과는 구분한다.

| 우선순위 | 항목 | 구분 | 담당 경계 | 계약 변경 |
| --- | --- | --- | --- | --- |
| P1 | 구독 생성 응답 유실 후 복구 | 기능 추가 | CAL·BATON | 필요 |

## 1. 구독 생성 응답 유실 후 복구

**현재 근거:** [SubscriptionService](../../src/main/kotlin/io/baton/cal/subscription/SubscriptionService.kt)의
`create`는 호출마다 새 구독 ID와 토큰을 만든다. 요청에는
[seasonId만 있다](../../src/main/kotlin/io/baton/cal/web/SubscriptionDtos.kt).
[PRD의 구독 자격 증명 계약](../PRD/0002_mvp-contract/spec.md)은 멱등성 키와 동일 응답 재사용이 없고,
응답 유실은 MVP 제한이라고 명시한다.

**사용자 영향:** DB 커밋 후 응답이 유실되면 BATON은 새 구독 ID도 모른다. 같은 요청을 다시 보내면
별도 구독이 생기며, 현재 개별 상태 조회만으로는 첫 구독을 찾아 정리할 수 없다. 토큰을 전달받지
못했을 가능성이 있으므로 이 상황을 곧바로 토큰 유출로 해석하지는 않는다.

**권장 범위:** BATON이 요청 전에 보관한 발급 요청 ID 또는 구독 ID로 하나의 구독을 식별하게 한다.
같은 식별자로 다른 시즌을 지정하면 충돌시키고, 응답을 잃어도 해당 구독의 존재를 조회할 수 있게 한다.
토큰 원문은 계속 저장하지 않는다. 유실된 자격 증명은 기존 구독을 명시적으로 회전해 다시 발급한다.
이는 이전 토큰 응답을 그대로 재전송하는 기능과 다르다. 회전도 응답을 잃을 수 있으므로 불확실한
상태의 사용자 안내와 재발급 절차를 함께 정해야 한다.

**최소 완료 기준:** 생성 커밋 후 연결 끊김, 같은 요청의 재전달·동시 전달에서 구독 한 개 유지,
같은 요청 ID의 시즌 충돌, 재발급 뒤 이전 URL의 `404`, 토큰 원문 미저장을 검증한다.

## 2. 실제 복원 스모크에서 완료 응답 확인

**현재 근거:** [복원 스크립트](../../scripts/smoke-oci-image.sh)의 376~385행은 최신 일정·취소·시즌
이름을 전달한 뒤 바로 복구 모드를 해제한다. 스크립트에는 시즌 매니페스트나 전체 완료 API 호출이
없다. 반면 [README 복원 절차](../../README.md)는 `COMPLETED` 확인 뒤 해제하도록 요구한다.
[RecoveryManifestHttpTest](../../src/test/kotlin/io/baton/cal/web/RecoveryManifestHttpTest.kt)는 API를
검증하지만 실제 `pg_restore`와 연결한 흐름은 아니다.

**영향:** OCI 스모크가 통과해도 복원된 데이터로 완료 API가 정상 작동하고, 잘못된 복구 상태에서
운영 절차가 멈추는지는 이 스크립트로 확인할 수 없다. 완료 API가 없거나 실패한다고 단정하는
문제가 아니라, 이미 구현된 경계를 함께 검증하지 않는 문제다.

**권장 범위:** 기존 대표 픽스처 복원 흐름에 새 복구 ID, 시즌 매니페스트 검증, 전체 완료 요청과
같은 요청 재시도를 추가한다. 예상 상태는 BATON 계약 픽스처에서 정하고, 복원 DB의 현재 값을
그대로 정답으로 삼지 않는다. `COMPLETED`를 확인한 뒤에만 모드를 해제한다.

**최소 완료 기준:** 취소 또는 최신 이름 누락 시 완료 실패와 발급 차단, 최신 상태 전달 후 완료 성공,
재시도 시 같은 완료 시각, 같은 세대에서 모드 해제 후 회전 성공을 기존 스모크 안에서 검증한다.
복구 모드를 CAL이 자동 해제하도록 바꾸지는 않는다.

## 3. 캘린더 앱별 구독 안내와 실제 호환성 검증

**현재 근거:** [HANDOFF](../../HANDOFF.md)는 실제 캘린더 앱의 이름 표시·갱신 검증을 미완료로
기록한다. 현재 테스트는 HTTP 계약과 iCalendar 표현을 검증한다.

**권장 범위:** BATON의 일회성 URL 표시 화면에서 앱별 구독 절차, 갱신 지연, URL 회전 뒤 재등록
절차를 안내한다. 사용자가 파일 가져오기를 선택해 변경·취소 반영을 기대하지 않도록 구독 절차를
분명히 설명한다. 화면 구현과 최종 사용자 권한은 BATON이 맡고, CAL은 피드 호환성을 검증한다.

공식 문서도 앱별 동작 차이를 보여준다. Google은 컴퓨터에서 URL로 캘린더를 추가하는 절차를,
Apple은 Mac 구독 캘린더의 자동 새로고침 설정을 제공한다.
Microsoft는 파일 가져오기가 자동 갱신되지 않고 URL 구독 갱신에는 24시간 이상 걸릴 수 있다고
안내한다. 이 안내는 CAL 피드의 실제 앱 호환성을 입증하는 자료가 아니므로 별도 실측이 필요하다.
[Google 안내](https://support.google.com/calendar/answer/37100?hl=en-uk),
[Apple 안내](https://support.apple.com/en-ie/guide/calendar/icl1024/mac),
[Microsoft 안내](https://support.microsoft.com/en-us/outlook/import-or-subscribe-to-a-calendar-in-outlook-com-or-outlook-on-the-web).

**최소 완료 기준:** Google Calendar 웹, Apple Calendar, Outlook 웹에서 같은 픽스처를 구독하고
생성·시간 변경·취소·재활성화·시즌 이름 변경·종일·시점·DST 경계를 확인한다. 앱·OS 버전,
확인 시각과 관측한 지연을 기록한다. 취소가 삭제·취소 표시·잔존 중 어떻게 보이는지도 기록한다.
토큰 회전으로 서버 접근이 차단되는 것과 이미 내려받은 일정의 화면 제거는 별도로 확인한다.

## 4. 공개 요청 제한과 운영 알림 연결

**현재 근거:** [공개 조회](../../src/main/kotlin/io/baton/cal/web/PublicCalendarController.kt)는
조건부 GET에서도 토큰 상태와 투영 메타데이터를 DB에서 확인한다. JSON 크기 제한은 공개 GET의
반복 요청 수를 제한하지 않는다. [HANDOFF](../../HANDOFF.md)는 공개 요청 제한, Prometheus
백엔드와 실제 프록시 검증을 후속 작업으로 둔다.

**권장 범위:** 선택한 역방향 프록시에서 요청률·동시 요청 제한을 먼저 적용하고 `429`와
`Retry-After` 동작을 확정한다. 캘린더 제공자의 공유 송신 IP를 고려해 정상 구독이 함께 막히지
않도록 조정한다. 수치는 운영 트래픽 측정으로 정한다. 기존 HTTP·인증·투영·DB 지표를 관측
백엔드에 연결하고 실제 `5xx`, 준비 상태 실패, 잠금 대기 증가에 알림을 붙인다.

**최소 완료 기준:** 실제 프록시에서 정상 구독과 초과 요청을 확인하고, 장애 한 건을 주입해 운영
알림이 도착하는지 검증한다. 토큰·전체 URL을 로그나 메트릭 라벨에 넣지 않고 관리 포트가 공개
라우팅되지 않는지도 같은 배포 환경에서 확인한다. CAL 자체에 별도 요청 제한 저장소를 먼저
도입할 필요는 없다.

## 5. 복구 진행 상태와 불일치 원인 조회

**현재 근거:** [RecoveryManifestService](../../src/main/kotlin/io/baton/cal/recovery/RecoveryManifestService.kt)는
여러 불일치를 `RECOVERY_MANIFEST_MISMATCH`로 반환한다.
[내부 컨트롤러](../../src/main/kotlin/io/baton/cal/web/InternalCalendarController.kt)는 복구 검증·완료
명령을 제공하지만 복구 상태 GET은 제공하지 않는다. 완료 요청에 필요한 원래 다이제스트를
모르면 운영자가 완료 기록을 다시 확인하기도 어렵다.

**권장 범위:** 내부 인증이 있는 읽기 전용 조회로 검증한 시즌 수, 저장된 완료 여부·시각과 현재
복구 모드를 제공한다. 시즌 단위로 일정 수·다이제스트와 이름 개정·다이제스트를 비교할 수 있게
한다. 우선 전체 시즌 목록을 제한 없이 반환하지 않고 개별 시즌 진단부터 시작한다. 저장된 완료
기록은 그 시점의 대조 결과이며 현재 상태가 계속 일치한다는 보증으로 표시하지 않는다.

**최소 완료 기준:** 조회 전후 저장 상태가 같고, 미완료·완료·없는 복구 ID를 구분한다. 불일치가
일정인지 이름인지 판단할 수 있으며 토큰·해시·피드 URL·원문 일정 내용은 응답에서 제외한다.
여기서 제외하는 해시는 구독 토큰 해시이며, 계약상 복구 다이제스트는 조회 대상이다.

## 6. 대량 수신·복구 부하 측정 후 처리 비용 개선

**현재 근거:** [스냅샷 수신](../../src/main/kotlin/io/baton/cal/snapshot/SnapshotIngestionService.kt)의
`APPLIED`마다 [시즌 전체 렌더링](../../src/main/kotlin/io/baton/cal/projection/SeasonProjectionService.kt)을
실행한다. [기존 부하 테스트](../../src/test/kotlin/io/baton/cal/projection/SeasonProjectionLoadTest.kt)는
DB에 항목을 미리 넣고 재구축 한 번을 측정한다. [성능 기준](../performance-baseline.md)의
10,000개 719~733밀리초를 10,000개 HTTP 수신·복구 전체 시간으로 해석할 수 없다.

**영향:** 빈 시즌에 새 항목 N개를 하나씩 적용하면 렌더링에 포함되는 항목 수의 합은
`1 + 2 + ... + N`이다. N이 10,000이면 50,005,000개 항목을 누적 처리한다. 이는 코드 경로의
계산이며 실제 소요 시간 예측은 아니다. 정확한 중복·낮은 개정 전달은 재구축하지 않으므로 같은
비용을 적용하지 않는다.

**권장 범위:** 우선 실제 수신 API에서 대량 최초 적재, 오래된 DB의 최신 변경 수신, 같은 시즌 동시
갱신과 공개 조건부 GET을 함께 측정한다. 처리량, 응답 지연, 잠금 대기와 최종 피드를 확인한다.
목표를 넘을 때만 크기가 제한된 묶음 수신과 묶음당 한 번 재구축을 검토한다. 기존 API의 `APPLIED`
응답은 피드 교체까지 커밋됐다는 뜻이므로, 응답 후 비동기 재구축으로 조용히 바꾸면 안 된다.

**최소 완료 기준:** 합의한 운영 데이터 규모와 수신량에서 목표를 충족하고, 중단·재전달·동시 갱신
후에도 최종 UID·SEQUENCE·취소 상태·ETag가 기존 단건 처리와 같다.

## 후속 검토와 문서 정리

- 취소 표식과 수신함의 무기한 보존은 현재 계약이다. 데이터가 늘면 테이블 크기와 백업 시간을
  측정하고 보존 정책을 논의하되, 삭제 작업부터 추가하지 않는다. 수신함 다이제스트는 현재
  [복구 상태 대조](../../src/main/kotlin/io/baton/cal/persistence/RecoveryManifestRepository.kt)에도 사용된다.
- 여러 시즌을 합친 구독은 반복적인 사용자 요구가 확인되면 검토할 수 있다. 그때 시즌 편입·제외와
  권한 철회 계약을 BATON과 먼저 정한다. 현재는 명시적인 MVP 제외 범위다.
- 안정 계약 승격과 운영 활성화는 [계약 릴리스 현황](../contract-release-history.md)의 절차를 따른다.
  게시된 계약 ZIP 안 PRD의 과거 상태 문구를 현재 상태와 다르다는 이유만으로 수정하지 않는다.
- [ADR-0002](../ADR/0002_technology-stack/adr.md)의 비용 절에는 매니페스트·완료 신호가 없다는 옛
  설명이 남아 있다. 같은 문서의 V8 결정 및 현재 구현과 맞게 정리할 필요가 있다. 이 검토에서는
  계약·구조 결정을 수정하지 않았다.

## 검증 결과와 한계

- `./gradlew --no-daemon test --rerun`: 기본 테스트 103개 통과, 실패·오류·건너뜀 0개.
