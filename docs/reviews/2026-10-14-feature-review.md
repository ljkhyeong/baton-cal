## 출력 변경 배포 뒤 전체 재생성

**현재 근거:** [SeasonProjectionService](../../src/main/kotlin/io/baton/cal/projection/SeasonProjectionService.kt)는
일정·시즌 이름 수신, 첫 구독, 시즌 재구축 때만 투영을 만든다.
[공개 피드](../../src/main/kotlin/io/baton/cal/web/PublicCalendarController.kt)는 저장된 바이트를 그대로 보낸다.
의존성 갱신 절차는 골든 검토로 끝나 배포 뒤 저장된 피드를 다시 만드는 단계가 없었다. 내부 API에는 시즌 목록이
없어 운영자가 DB를 직접 조회해 시즌별로 재구축해야 했다.

**영향:** 시간대 규칙이 바뀐 iCal4j를 배포하면 입력의 DST 공백 판정은 새 규칙을 쓰지만, 수신이 없는 시즌의 피드는
이전 `VTIMEZONE`을 계속 보낸다. 피드의 `VTIMEZONE`을 쓰는 앱은 바뀐 규칙이 적용되는 일정을 다른 시각으로 표시할 수
있다. 출력 형식 변경도 수신이 있었던 시즌에만 적용된다. 운영 데이터가 없는 지금은 영향이 없고 운영 배포 뒤 첫
출력 변경부터 해당한다.

**처리:**

- 투영이 저장된 모든 시즌을 UUID 순서로 한 번씩 재구축한다. 시즌 잠금과 Last-Modified 규칙은 기존 시즌 재구축과
  같다. 출력이 같은 시즌은 행을 다시 쓰지 않는다.
- 시즌마다 따로 커밋해 잠금을 한 시즌으로 제한한다. 실패하면 앞서 커밋한 시즌은 유지되고 같은 요청으로 남은
  시즌을 처리한다. 작업 상태 테이블과 스케줄러는 두지 않았다.
- 시작 시 자동 실행은 인스턴스마다 전체 렌더링을 반복하고, 배포 중 이전 인스턴스가 이전 출력으로 다시 쓸 수
  있다. 모든 인스턴스 배포 뒤 운영자가 호출하는 방식을 택했다. 절차는
  [README](../../README.md#캘린더-출력-변경-배포)에 있다.
- 응답의 `changedSeasonCount`로 배포한 출력이 실제 저장 데이터에서 바뀌었는지 확인한다. 로컬 골든 검토 결과와
  다르면 원인을 확인한다.
- 계약은 게시 전 작업 후보 `1.1.0-rc.3`에 추가했다. 기존 경로·스키마·골든과 BATON 연동은 바꾸지 않았다.

**검증:** `ProjectionRebuildAllHttpTest`가 실제 PostgreSQL에서 이전 출력으로 저장한 시즌만 교체되는지, 나머지
시즌의 바이트·ETag·Last-Modified와 구독 주소가 유지되는지, 재요청이 아무것도 바꾸지 않는지 확인한다. 두 번째
시즌의 잠금 실패는 `503 SERVICE_BUSY`이며 첫 시즌의 커밋을 유지하고, 재요청이 남은 시즌만 처리하는 것도 확인한다.
인증 `401`, 복구 모드 허용과 응답 스키마도 기존 테스트에 추가했다. 실행 결과는 [인수인계](../../HANDOFF.md)에 기록한다.

**남은 위험:** 배포한 버전이 저장된 일정을 렌더링하지 못하면(예: 새 시간대 데이터에서 저장된 TZID가 다른 식별자의
별칭이 됨) 전체 재생성은 그 시즌에서 `500`으로 멈추고 응답에 시즌을 표시하지 않는다. 같은 시즌의 수신·재구축도
실패하는 기존 위험이며, 의존성 갱신 절차의 골든 검토와 운영 데이터의 TZID 확인으로 배포 전에 걸러야 한다.

## 보류·결정 필요 항목

### 캘린더 갱신 주기 힌트

[RFC 7986 5.7절](https://www.rfc-editor.org/rfc/rfc7986.html#section-5.7)의 `REFRESH-INTERVAL`은 폴링 간격의
최솟값을 제안하며 클라이언트가 조회를 제한할 때 쓴다. 변경 반영을 앞당기는 값이 아니다. `X-PUBLISHED-TTL`은
Microsoft 확장이며 현재 Outlook이 따른다는 공식 문서를 찾지 못했다.
[앱별 안내](../calendar-subscription-guide.md#앱별-등록-방법)대로 Google·Outlook 웹은 제공자 주기, Apple Mac은
사용자가 고른 자동 새로고침 주기를 따른다. 실제 앱 검증에서 기본 갱신 주기와 반영 지연을 기록한 뒤 조회 제한이
필요하면 새 계약 후보로 검토한다.

### 구독별 마지막 조회 날짜

[구독 상태 확인](../calendar-subscription-guide.md#구독-상태-확인) 안내는 주소 사용 가능이 앱 등록을 뜻하지
않는다고 설명한다. CAL이 구독별 최근 조회 날짜를 저장하면 BATON이 등록 여부와 갱신 중단을 보여줄 수 있다.
파일 가져오기도 한 번 조회하므로 첫 조회만으로는 구독 등록을 판정할 수 없고, 날짜가 계속 갱신되는지로 판단해야 한다.

진행하려면 다음을 정한다.

- 기록 단위와 보존 기간, 폐기·회전 때 삭제 여부. 현재 공개 프록시와 CAL은 요청 경로·IP를 기록하지 않아 구독별
  조회 기록이 없다.
- 읽기 전용인 공개 GET·HEAD에서 하루 한 번 갱신하는 쓰기와, 쓰기 실패 때도 피드를 응답하는 처리.
- `subscription-status.v1`은 추가 필드를 거부하므로 새 스키마나 별도 경로, BATON 클라이언트·화면 문구.

### iCal4j 4.4.0

4.3.0과 4.4.0 JAR의 `zoneinfo`·`zoneinfo-global` 파일 1,192개는 목록과 내용이 같고 모두
`PRODID:-//tzurl.org//NONSGML Olson 2025a//EN`이다. 갱신해도 시간대 규칙은 바뀌지 않는다. 출력 바이트와
API 호환성은 [의존성 갱신 절차](../../contracts/README.md#의존성과-골든-갱신-절차)의 골든 검토로 확인하고,
게시 계약 문서의 `iCal4j 4.3.0` 표기도 함께 바꿔야 한다.

### 피드 gzip 압축

공개 프록시는 `Accept-Encoding`을 CAL로 전달하지 않아 현재 피드를 압축하지 않는다. Nginx gzip을 켜면
[nginx 1.7.3 변경](https://nginx.org/en/CHANGES-1.8)에 따라 강한 ETag가 약한 ETag로 바뀌고 `Content-Length`가
빠진다. PRD-0002의 강한 ETag·HEAD 파일 크기 계약을 바꿔야 하므로 실제 전송량 문제가 확인될 때 검토한다.

### `METHOD:PUBLISH`

[RFC 5545 3.8.7.2절](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.7.2)에 따르면 `METHOD`가 없는
현재 피드의 `DTSTAMP`는 정보가 마지막으로 바뀐 시각이다. `METHOD`를 넣으면 객체 생성 시각을 뜻하므로
`sourceUpdatedAt` 매핑을 다시 정해야 한다. 취소 표시 방식은 앱마다 다르므로 실제 앱 검증 결과를 본 뒤 판단한다.

## 후속 진행 — 2026-10-16

사용자가 구독별 최근 조회일을 CAL만 구현하고, 나머지는 권장대로 진행하도록 정했다.

**구독 최근 조회일:** 공개 GET·HEAD·`304`가 성공하면 `calendar_subscription.last_fetched_on`에 UTC 날짜를
기록한다. 조회와 다른 문장으로 실행해 쓰기 실패와 행 잠금이 피드 응답을 막지 않게 했다. `FOR UPDATE SKIP LOCKED`로
회전·폐기가 잡은 행은 기다리지 않고, 날짜는 앞으로만 옮기며 같은 날에는 쓰지 않는다. 회전·폐기 때 비우고, 이전
세대 구독은 복원된 날짜 대신 `null`을 반환한다. 기존 `subscription-status.v1`은 추가 필드를 거부하므로 바꾸지 않고
새 경로와 `subscription-activity.v1`을 추가했다. 조회 시각·IP·클라이언트 정보와 이력은 저장하지 않는다.
`SKIP LOCKED`를 지운 변형에서 잠금 테스트가 실패하는 것도 확인했다. BATON 클라이언트와 구독 화면 연결은 남아 있다.

**iCal4j 4.4.0:** `zoneinfo`·`tz.alias`가 같고 렌더러 골든 테스트가 같은 바이트로 통과했다. 시간대 외부 갱신
기본값은 계속 꺼져 있다. 4.4.0은 `java.time` `ZoneRulesProvider` 서비스 등록을 없앴지만 CAL은 `ZoneId.of`를 쓰지
않고 iCal4j `VTIMEZONE`으로 규칙을 만든다. JSpecify 표기로 `VTimeZone.timeZoneId`가 nullable이 되어 테스트만
`TZID` 속성으로 읽도록 바꿨다.

**복원 절차:** 백업 이후 렌더러가 바뀌었다면 재전달만으로는 변경 없는 시즌이 이전 출력으로 남는다. 복구 모드에서
전체 재생성을 실행하도록 README·PRD-0002 복원 절차와 OCI 복원 스모크에 넣었다.

추가 점검에서 알림 규칙은 5xx·잠금 지연·인증 실패·수신 거부·TLS·공개 경로를 이미 다뤄 바꾸지 않았다.
검증 결과는 [인수인계](../../HANDOFF.md)에 기록한다.
