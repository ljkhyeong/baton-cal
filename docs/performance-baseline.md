# 시즌 투영 성능 기준

## 목적

시즌 전체 투영 재구축이 동기식 HTTP 처리로 유지 가능한 규모인지 확인하고, 런타임·PostgreSQL·
iCal4j 변경 뒤 성능 회귀를 비교할 개발 기준을 남긴다. 이 수치는 운영 트래픽과 장비를 반영한
서비스 수준 목표(SLO)가 아니다.

## 측정 범위

`SeasonProjectionLoadTest`는 실제 PostgreSQL에 한 시즌의 최신 원본 행을 넣은 뒤
`SeasonProjectionService.rebuild` 한 번을 측정한다. 측정 구간에는 원본 조회, 도메인 복원,
iCal4j 직렬화와 투영 upsert가 포함된다. Testcontainers 기동과 데이터 준비 시간은 제외한다.

환경은 2026년 8월 30일 기준 Apple Silicon `arm64`, Java 25 툴체인, Docker의 PostgreSQL 18.6이다.
각 규모를 새 시즌으로 5회 측정했다.

| 시즌 항목 수 | 재구축 시간 범위 | iCalendar 표현 크기 |
| ---: | ---: | ---: |
| 500 | 131~155밀리초 | 122,560바이트 |
| 1,000 | 104~108밀리초 | 245,060바이트 |
| 5,000 | 396~406밀리초 | 1,229,060바이트 |
| 10,000 | 719~733밀리초 | 2,459,060바이트 |

## 해석과 사용법

- 현재 개발 환경에서는 10,000개 전체 재구축도 1초 안에 끝났다. 첫 실행 준비 비용과 측정 흔들림이
  있으므로 작은 규모의 단일 값보다 반복 범위와 큰 규모의 추세를 본다.
- PostgreSQL 잠금 대기 5초, SQL 실행과 Spring 트랜잭션 30초 기본값은 이 개발 기준보다 충분히
  크다. 제한 시간을 성능 목표로 해석하거나 부하 증가를 가리는 수단으로 늘리지 않는다.
- 운영 데이터 분포, 동시 요청, 네트워크와 장비가 다르므로 배포 환경의 SLO는 별도로 정한다.
- Java, PostgreSQL, iCal4j, SQL 또는 렌더링 경로를 바꾸면 같은 명령으로 다시 측정하고 이 문서의
  환경과 결과를 함께 갱신한다.

```shell
./gradlew --no-daemon projectionLoadTest
```

이 작업은 `load` 태그만 실행하며 기본 `test`에는 포함되지 않는다.

## 실제 HTTP 최초 적재와 동시 변경

2026-09-05에 `SnapshotIngestionLoadTest`로 실제 임의 포트의 Spring MVC 서버와 PostgreSQL
18.6을 연결해 측정했다. 환경은 Apple Silicon `arm64`, 테스트 JVM Java 25.0.3, 기본 DB 풀 10개다.
프록시·공인 네트워크를 거치지 않는 개발 장비의 1회 측정이며 앱·DB 기동 시간은 제외한다.

```shell
./gradlew --no-daemon ingestionLoadTest -PloadItemCount=1000
```

`ingestion-load` 태그는 기본 `test` 및 기존 `projectionLoadTest`에서 제외한다. `loadItemCount`는
기본 1,000이며 2 이상으로 지정한다. 매 실행은 격리된 빈 DB에서 시작한다. 같은 크기로 다시
측정할 때는 `--rerun`을 붙여 이전 테스트 결과를 재사용하지 않게 한다.

1. 한 시즌에 개정 0 일정 1,000개를 HTTP로 순차 적재한다.
2. 두 작업자가 같은 시즌의 서로 다른 항목을 개정 2로 동시 변경한다. 짝수 항목 500개는 취소한다.
   20번째 항목마다 같은 이벤트 재전달과 아직 받은 적 없는 낮은 개정 1을 추가로 전달한다.
3. 별도 작업자가 ETag 조건부 GET을 보내고 각 응답 뒤 25ms 간격으로 다음 요청을 보낸다.
   변경 구간이 끝나면 최종 UID·SEQUENCE·취소 상태와 전체 재구축 후 ETag 일치를 검증한다.

| 측정 구간 | 요청 수 | 구간 시간 | 초당 요청 수 | p50 | p95 | 최대 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 최초 적재 | 1,000 | 38.694초 | 25.84 | 39.222ms | 63.189ms | 194.957ms |
| 두 작업자 변경 | 1,000 | 65.741초 | 15.21 | 129.879ms | 136.345ms | 193.716ms |
| 변경 중 중복·낮은 개정 | 100 | 위 변경 구간과 공유 | 1.52 | 66.525ms | 69.733ms | 92.329ms |
| 변경 중 조건부 조회 | 2,061 | 위 변경 구간과 공유 | 31.35 | 3.052ms | 5.359ms | 30.681ms |

변경 구간의 잠금 획득 1,100회에서 누적 획득 시간은 58,971.960ms, 평균은 약 53.611ms였다.
이 지표는 순수 DB 대기만이 아니라 시즌 잠금 획득 SQL 처리 시간을 포함한다. Micrometer가 해당
측정 창에 기록한 최대는 92.533ms이며 최초 적재와 변경 구간을 엄격히 분리한 최대가 아니다.
조회는 200이 999회, 304가 1,062회였다. 304 본문은 비어 있었고 최종 1,000개 UID·개정 2,
500개 취소와 재구축 후 동일 ETag를 확인했다. HTTP 오류나 일관성 검증 실패는 없었다.

공유 구간의 초당 요청 수는 혼합 작업 중 관측값이다. 중복 수신만의 최대 처리량이나 공개 GET의
최대 처리량을 뜻하지 않는다. 정확히 같은 기존 개정의 페이로드는 이벤트 ID가 달라도 `DUPLICATE`이므로,
`STALE` 측정에는 개정 0과 2 사이의 미수신 개정 1을 사용한다.

기존 10,000개 **재구축 한 번**의 719~733ms를 10,000개 **단건 HTTP 전체 수신** 시간으로 해석하면
안 된다. `APPLIED`마다 시즌 전체를 동기식 재구축하므로 최초 적재는 누적해서
`N × (N + 1) / 2`개 항목을 렌더링한다. 1,000개에서는 500,500개다. 이 결과만으로 다른 규모의
완료 시간을 선형 추정하지 않는다.

운영 시즌 크기·동시 수신량·복구 목표 시간은 아직 합의되지 않았다. 단건 응답은 피드 교체까지
커밋됐다는 기존 계약을 유지한다. 운영 목표와 위 비용이 맞지 않으면 크기를 제한한 묶음 수신과
묶음당 한 번 재구축을 새 계약으로 검토한다. 이 측정에서는 배치 API나 비동기 재구축을 도입하지 않았다.
